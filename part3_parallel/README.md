# Часть 3. Многопоточная и многопроцессорная аугментация

Конвейер «производитель - потребители»: потоки читают файлы, пул
процессов выполняет аугментацию, в конце измеряется ускорение.

## Запуск

```bash
cd part3_parallel
python -m app.cli                    # 150 файлов, 4 потока, 4 процесса
python -m app.cli --limit 40 --processes 2
python -m app.cli --size 192 --copies 2 --processes 6
python -m app.cli --no-sequential     # только конвейер, без сравнения
```

## Архитектура

```
[producer thread] -> queue.Queue(paths)
        |
        v
[reader-1 ... reader-N] -> queue.Queue(arrays)
        |
        v
[main] -> multiprocessing.Pool.apply_async(augment_task, callback)
        |
        v
   results -> augmented.npy
```

- Поток-производитель кладёт в очередь пары `(индекс, путь)` и по
  одному «стопу» (`None`) на каждого читателя.
- Читатели забирают пути, читают изображения через Pillow и отдают
  массивы во вторую очередь. Каждый файл логируется с временем чтения.
- Главный поток передаёт массивы в пул процессов методом
  `apply_async()` с callback - результат складывается в словарь под
  блокировкой.
- Общий счётчик прочитанных файлов защищён `threading.Lock`
  (класс `ProcessedCounter`).
- В конце вызываются `pool.close()`, `pool.join()` и `join()` всех
  потоков; количество живых дочерних процессов печатается отдельно.

## Почему аугментация в процессах, а чтение в потоках

Чтение файла - операция ввода-вывода: поток ждёт диск, GIL на это
время освобождается, поэтому потоки дают выигрыш почти без затрат.
Аугментация - чистое вычисление над массивами, а GIL в CPython
разрешает исполнять байт-код только одному потоку. Поэтому
CPU-bound часть уходит в процессы, у каждого из которых свой GIL.

## Аугментация

Каждая копия проходит цепочку:

1. поворот на случайный угол до 15 градусов (билинейная
   интерполяция, обратное преобразование координат);
2. отражение по случайной оси;
3. гауссов шум (sigma = 0.05) с обрезкой в диапазон [0, 1].

## Замеры

`performance_report.json` содержит время последовательной и
параллельной версий, ускорение, число потоков и процессов, время
запуска пула процессов.

```json
"sequential": {"seconds": 0.6900, "per_file_ms": 4.6},
"parallel":   {"seconds": 0.4900, "per_file_ms": 3.3,
               "startup_seconds": 0.5300},
"speedup": 1.4
```

Время параллельной версии замеряется после прогрева пула: на Windows
каждый процесс запускается заново и импортирует NumPy, поэтому запуск
(около 0.5 с) показан отдельным полем. Разброс ускорения при повторных
запусках - 1.4-1.5 раза. На малом объёме данных накладные расходы на
передачу массивов могут съесть весь выигрыш - это видно при сравнении
`--limit 30` и полного набора.

## Проверка корректности

Программа дополнительно сравнивает наборы, полученные
последовательной и параллельной версиями (`np.allclose`) и печатает
`Наборы совпадают: True` - значит распараллеливание не изменило
результат.
